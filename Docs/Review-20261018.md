## 2. 已复现问题与后续验收决定

### R-01 原标准下 [P1] 删除来源后历史内容仍被发送（已接受限制）

- 位置：[DiscussionPipeline.swift](../Sources/ReaderAgent/DiscussionPipeline.swift)，`history()` 第 224–240 行，尤其第 235–238 行。
- 触发：主书与另一本书跨书讨论；保存引用第二本书的历史回答；删除第二本书的文件并保留笔记；在原讨论继续追问主书。
- 原验收预期（已调整）：历史回答引用的来源必须重新通过当前书籍状态、版本、允许书籍与阅读区间检查；来源失效的内容不能作为有效历史依据重新发送。
- 实际：代码只检查消息状态，以及“原来是全书、现在是已读”这一种范围收紧情况。它不检查历史回答的 `citations`、当前来源可用性或定位范围。
- 复现结果：第二本书状态确认为 `sourceUnavailable` 后，下一轮 `generation` 请求仍包含带该书正文的历史回答，记录 `deleted-book history messages forwarded: 1`。
- 当前决定：READ-05 与 ACCEPT-06 的来源重新校验保证限定于新检索、扩展与新召回记忆。历史回答保留为会话快照，当前未逐轮重新校验引用来源的可用性、版本或定位范围；删除书籍文件并保留笔记后，旧回答摘录仍可能发送给模型。因此不承诺删除来源后历史摘录自动撤回，也不承诺历史上下文完全符合当前阅读范围。 按用户授权接受为限制，原始失败记录不改写。
- 可选改进：构造历史上下文时逐条核验引用来源，过滤不再允许的轮次，或仅重新组装仍有效的证据；同时遵守本轮策略是否启用 history。为删除、版本变化、跨书范围收紧和已读区间变化补回归测试。

复现使用内存 SQLite 与确定性模型桩：先构造一条已有已核查回复，随后调用真实删除服务，再经过真实讨论编排检查模型请求。它不依赖真实模型偶然输出，也不接触用户阅读数据。

### R-02 原标准下 [P2] 历史消息绕过上下文总预算（已接受，不再阻塞）

- 位置：[DiscussionPipeline.swift](../Sources/ReaderAgent/DiscussionPipeline.swift)，第 97–98、119–121、237–240 行；[Context.swift](../Sources/ContextEngineering/Context.swift) 的 `generationMessages`。
- 触发：一次较长问题被保存为历史，之后在同一讨论中继续提问。
- 原验收预期（已调整）：证据与历史共同遵守 6,000 Token 的上下文预算；历史用户问题也需要计算并裁剪。
- 实际：`ContextAssembler` 只对证据集合执行预算；随后直接附加 `history()`。历史助手回答限为 400 Token，但用户消息原样附加；最后限制 8 条消息并不能限制 Token 总量。
- 复现结果：使用一条 8,000 个中文字符的历史问题，历史消息单独估算为 **8,026 Token**，尚未加本轮证据就已超过 **6,000** 的配置。
- 原对应要求：CTX-03、10.2 的证据与历史共同预算；这两处标准已同步调整。
- 用户决定（2026-10-18）：接受现有行为，6,000 Token 仅限制组装证据；附加历史保留最近最多 4 组问答（8 条消息），每条历史助手回答最多估算 400 Token，历史用户问题不额外裁剪。不要求应用层统一限制证据与历史总量，服务端模型输入限制仍适用。
- 当前状态：**已接受的限制，不再阻塞验收**。这次调整的是验收标准，并未修复原探针所展示的行为，也未把原失败记录改为通过。统一预算可作为后续可选改进。
